# Recorded performance numbers, in nanoseconds. Lower is better.
#
# BUILD-HOST NUMBERS. They are taken on the Linux build host by
# tools/build-host-tests.sh and mean nothing on any other machine. A laptop
# running dev servers sits at load 20-30 and its readings move by half between
# runs.
#
# A run slower than its number by more than the margin (default 20%) fails.
# A run faster prints the new number and asks you to record it, deliberately,
# in the commit that earned it. Recording a slower number is a decision to
# accept a regression and has to be argued for in the commit message.
#
# docs/PERFORMANCE.md has the real production-shaped measurements and how they
# were taken. These are here to catch a change that makes something markedly
# slower, nothing more.
#
# ── What the targets are ─────────────────────────────────────────────────────
#
# Both render an HTML page end to end over the socket, from the examples
# repository, whose content is committed so the same bytes are rendered on every
# machine.
#
#   render:minimal     example 01, `/`. A 10-line template over 185 bytes of
#                      params, so what is left is the FIXED per-request cost.
#                      The defect this check exists for was that shape: `App`
#                      spent 0.63 ms per page copying its own config regardless
#                      of page size.
#
#   render:blog-index  example 05, `/blog`. The post index rendered from 113 KB
#                      of posts.json, iterating every post. The per-item cost,
#                      which a minimal page cannot see.
#
# ── 2026-09-14: `render:capabilities` is gone ────────────────────────────────
#
# It measured a deployment's `/capabilities` against its own content, through
# `deploy/rendered/prod/configs/m6-html.conf`. m6 is a generic web system and
# could not measure itself: a checkout with no site beside it failed this check
# rather than running it, and the recorded 2170589ns described one site's 84 KB
# content file, so it meant nothing to anyone else.
#
# Its number is deliberately not carried over. Neither new target renders the
# same page from the same bytes, so translating it would be inventing a
# measurement. A deployment can still measure its own content by setting
# PERFCHECK_SITE, and should keep its own number in its own repository.
#
# ── No numbers recorded yet ──────────────────────────────────────────────────
#
# The two targets below have never been measured on the build host. Until they
# are, this check reports each reading and passes, which is honest: it has
# nothing to compare against and says so rather than inventing a ceiling.
#
# Record them with, on the build host and nowhere else:
#
#     tools/perfcheck.sh --update
#
# For reference only, NOT a baseline: on a macOS laptop at load, the minimum of
# five rounds was 92020ns and 1005416ns respectively. Laptop readings move by
# half between runs and are not comparable with the build host's.
