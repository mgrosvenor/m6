# Recorded performance numbers, in nanoseconds. Lower is better.
#
# BUILD-HOST NUMBERS. They are taken on the Linux build host by
# tools/build-host-tests.sh and mean nothing on any other machine. A laptop
# running dev servers sits at load 20-30 and its readings move by half between
# runs.
#
# A run slower than its number by more than the margin (default 20%) fails.
# A run faster prints the new number and asks you to record it, deliberately,
# in the commit that earned it. Recording a slower number is a decision to
# accept a regression and has to be argued for in the commit message.
#
# ── 2026-09-27: both numbers moved, and why these values ─────────────────────
#
# The release profile landed (m6 4ce64a9: lto = "fat", codegen-units = 1,
# strip = "symbols", panic = "abort", overflow-checks = true). m6 had no
# [profile.release] at all before it, so every release ever built took cargo's
# defaults.
#
#   render:minimal     201827 -> 174101   -13.7%
#   render:blog-index 1784823 -> 1454253   -18.5%
#
# THREE RUNS on the build host at load 0.12, five readings each, plus an earlier
# gate run. Every reading is in tools/perf-history.jsonl. The readings:
#
#   render:minimal     180204 170456 162619 194755 157481
#                      197936 161793 196141 167908 174101
#                      166299 170732 189051 184965 234618
#   render:blog-index 1412852 1436586 1464478 1470098 1454253
#                    1491985 1386017 1485902 1441406 1393243
#                    1459256 1415412 1399216 1477220 1532813
#
# THESE ARE MEDIANS. Owner's decision, 2026-09-27: work with medians, not minima
# or maxima. A minimum is the best reading the machine ever managed and no request
# costs that. A maximum is whatever else the box was doing. The median is the
# typical cost, and a latency floor should be made of typical.
#
# The three run medians, and the median of them, which is what is recorded:
#
#   render:minimal     170456 174101 184965  ->  174101
#   render:blog-index 1454253 1441406 1459256 -> 1454253
#
# ON MINIMA THE SAME RUNS CLAIMED MORE: -17.6% and -20.6%, against -13.7% and
# -18.5% here. The minimum flattered the result by about four points, which is
# the reason for the change rather than an argument against it.
#
# Run 3 read 166299 to 234618 on render:minimal inside one run on an idle machine,
# a 41% spread, which is what the 20% margin exists to absorb.
#
# Every reading is in tools/perf-history.jsonl with the box it came from.

# docs/PERFORMANCE.md has the real production-shaped measurements and how they
# were taken. These are here to catch a change that makes something markedly
# slower, nothing more.
#
# ── What the targets are ─────────────────────────────────────────────────────
#
# Both render an HTML page end to end over the socket, from the examples
# repository, whose content is committed so the same bytes are rendered on every
# machine.
#
#   render:minimal     example 01, `/`. A 10-line template over 185 bytes of
#                      params, so what is left is the FIXED per-request cost.
#                      The defect this check exists for was that shape: `App`
#                      spent 0.63 ms per page copying its own config regardless
#                      of page size.
#
#   render:blog-index  example 05, `/blog`. The post index rendered from 113 KB
#                      of posts.json, iterating every post. The per-item cost,
#                      which a minimal page cannot see.
#
# ── 2026-09-14: `render:capabilities` is gone ────────────────────────────────
#
# It measured a deployment's `/capabilities` against its own content, through
# `deploy/rendered/prod/configs/m6-html.conf`. m6 is a generic web system and
# could not measure itself: a checkout with no site beside it failed this check
# rather than running it, and the recorded 2170589ns described one site's 84 KB
# content file, so it meant nothing to anyone else.
#
# Its number is deliberately not carried over. Neither new target renders the
# same page from the same bytes, so translating it would be inventing a
# measurement. A deployment can still measure its own content by setting
# PERFCHECK_SITE, and should keep its own number in its own repository.
#
# ── First readings, 2026-09-14, on the build host ────────────────────────────
#
# Taken at load average 0.20 on the 4-core Linux build host, which is the only
# machine these mean anything on.
#
# Each perfcheck round is already the minimum of five requests. Three rounds were
# run and the MEDIAN of the three is recorded, rather than the best of them: the
# lowest reading is the one the machine was least busy for, and recording it would
# set a ceiling the same code fails to meet on an ordinary afternoon.
#
#   render:minimal      190261, 203222, 201827 ns   -> median 201827  (6.8% spread)
#   render:blog-index  1781799, 1848274, 1784823 ns -> median 1784823 (3.7% spread)
#
# Both spreads sit well inside the 20% margin, which is the margin doing its job:
# it is there for exactly this variation and not much wider than it.
#
# For reference only, NOT a baseline: the same two targets on a macOS laptop read
# 92020ns and 1005416ns. The laptop is roughly twice as fast here and its readings
# move by half between runs, which is why the recorded numbers are the build
# host's and comparing the two tells you nothing.
#
